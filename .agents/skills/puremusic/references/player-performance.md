# 播放页性能规则

## 目标

新增样式和动效应主要增加绘制内容，不应按组件数量叠加位置查询、Ticker、Widget 重建、图片解码和无上限缓存。视觉流畅度是约束，不通过明显降低背景帧率、流速或呼吸幅度掩盖性能问题。

## 驱动模型

- 切歌、seek、播放状态变化、歌词加载完成、路由重新可见：使用离散 notifier，立即读取一次底层真实位置并同步 UI。
- 连续进度：当前可见组件使用共享 Ticker 或本地 `Stopwatch` 推进，约 1 秒低频校准；不让每个组件订阅高频 `positionStream`。
- 歌词行：只有当前逐字行和正在运行的间奏允许逐帧更新，普通行只在状态变化时重绘。
- 动态背景：只在页面可见且播放或颜色过渡时运行；频谱没有消费者时不计算。

## 每帧路径

允许读取已缓存标量、插值、更新 `CustomPainter` 和复用固定长度缓冲。

不执行 FFI 查询、图片解码、调色板提取、文件访问、Future 创建、大集合分配、整页 `setState`，也不重复创建滤镜或 Paragraph。

## 内存生命周期

- 缓存同时定义键、上限、淘汰策略和清理时机。
- 切歌期间允许短暂保留新旧两套视觉资源，过渡结束后释放旧资源。
- 低内存清理分级执行：先清不可见和可重建缓存，再缩小共享缓存；普通切歌时不清空全部缓存。
- Controller、Ticker、StreamSubscription、Timer 和原生缓冲由创建者负责停止与释放。
- 不在播放页 `dispose` 中清空 `nowPlayingCover`、`_nowPlayingCoverBytes` 或 `_preExtractedPalette`，避免破坏封面过渡。

## 修改前检查

1. 找出同类组件现有的驱动源，确认能否复用。
2. 写清组件何时启动、暂停和销毁。
3. 确认每帧是否触发 Widget 重建、FFI、解码或分配。
4. 确认缓存上限和切歌时的新旧资源交接。
5. 涉及受保护功能时，先按 `AGENTS.md` 和 `SKILL.md` 告知用户。用户同意后可以进行修改。

## 修改后检查

1. 搜索新增的 `Ticker`、`Timer.periodic`、`positionStream`、`spectrumStream` 和 `setState`，逐一核对生命周期。
2. 确认可见性切换、暂停、切歌、seek、返回播放页和无歌词状态都不会留下常驻工作。
3. 对修改文件执行格式化、静态分析和 diff 检查；完整构建和完整测试由用户明确要求后执行。
4. 性能结论来自相同歌曲、窗口和样式下的运行态对比，至少观察稳定播放与连续切歌两个阶段。
